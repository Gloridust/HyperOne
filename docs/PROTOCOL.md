# HyperOne Protocol (v1 prototype)

HyperOne is a research prototype of a TLS-camouflaged circumvention transport.
Its goal is to resist both **active probing** and **passive traffic analysis**
better than a straightforward REALITY/VLESS deployment, by combining a
ShadowTLS-style relay front with an inner channel that is framed as ordinary
TLS 1.3 application data.

This document describes what the prototype actually implements today and, in a
separate section, the properties it does **not** yet provide. It is written so
the design can be scrutinised; nothing here should be read as a claim that the
protocol is undetectable. No such claim is possible.

## 1. Threat model

The adversary is an on-path censor that can:

- observe every byte and packet timing on the link (passive DPI);
- actively connect to the server and send arbitrary bytes (active probing);
- replay traffic it has previously recorded;
- block or reset flows it judges to be a proxy.

The adversary does **not** hold the pre-shared key (PSK) and cannot break
X25519/ChaCha20-Poly1305/HMAC-SHA256.

The design goals, in order:

1. An active probe must be unable to distinguish the server from the genuine
   camouflage site it fronts.
2. A passive observer must not find a cheap, reliable feature that separates a
   HyperOne flow from normal HTTPS to that site.
3. Compromise of one session must not compromise others.

## 2. Components

```
client browser --SOCKS5--> h1-client --TLS-looking stream--> h1-server --> target
                                                                 |
                                       unauthenticated peers ----+--> real camouflage site
```

## 3. Handshake and authentication

The client speaks a genuine TLS 1.3 ClientHello generated by **uTLS** with a
current Chrome fingerprint. The HyperOne server does not terminate this
handshake: it relays it to a real camouflage site, exactly as ShadowTLS does,
so the certificate, extensions and post-handshake behaviour a probe sees are
the real site's.

Authentication is carried in the 32-byte `session_id` of the ClientHello, a
field that is opaque on the wire and echoed verbatim by a TLS 1.3 server in
compatibility mode. Its layout:

| bytes | meaning |
|-------|---------|
| 0:4   | big-endian unix seconds |
| 4:16  | random nonce |
| 16:32 | `HMAC-SHA256(PSK, epoch‖nonce‖clientRandom)[:16]` |

The tag commits to the connection's own TLS `random`, so it cannot be lifted
onto a different handshake without the PSK. The server:

1. parses the ClientHello, extracts `session_id` and `random`;
2. rejects tags whose timestamp is outside a ±90 s skew window;
3. verifies the HMAC in constant time;
4. only *then* consults a replay cache keyed on `nonce‖tag`.

Checking the replay cache last means an adversary without the PSK cannot make
the cache grow. A tag outside the skew window can never be replayed because the
timestamp check fails first, which bounds the cache to the skew window.

To a peer that does not hold the PSK, an authenticated `session_id` is
indistinguishable from the random session-ticket id a resuming browser sends.

## 4. Fallback (the active-probing defence)

If the first record is not a ClientHello, or the tag does not verify, the
server dials the camouflage site, replays the bytes it already read, and
splices the two connections for the lifetime of the flow. The probe therefore
completes a real TLS handshake against the real certificate and can interact
with the real site. There is no HyperOne-specific response for a probe to
fingerprint, because HyperOne never generates one.

## 5. Handoff to the inner channel

Both peers observe the `ServerHello.random` on the wire (the client tees its
inbound bytes; the server parses the record it relays). Combined with the
`ClientHello.random` and the PSK, each side derives directional keys:

```
salt = clientRandom ‖ serverRandom
k_c2s ‖ k_s2c = HKDF-SHA256(PSK, salt, "hyperone/v1 inner keys")
```

The client finishes the real TLS handshake (so the camouflage site sees a
complete, valid session), then stops using the TLS session and sends inner
records on the same socket. The server, which has been relaying the client's
real handshake records to the backend, trial-decrypts each inbound
application-data record under `k_c2s` at counter 0. The client's genuine TLS
Finished (encrypted under the real TLS keys) fails to open; the first inner
record succeeds. That success is the handoff: the server closes the backend and
switches the connection to the tunnel. False-positive probability is ~2⁻¹²⁸.

## 6. Inner record framing

Every inner record is byte-identical in shape to a TLS 1.3 application_data
record:

```
0x17 0x03 0x03  length(2)  ChaCha20-Poly1305(plaintext)
```

The plaintext's first byte is a type: data or padding. Padding records are
authenticated and silently dropped by the receiver, so the shaper can inject
cover bytes and break up size patterns without the stream layer seeing them.
The nonce is a per-direction 64-bit counter; keys are session-unique, so
counters never collide.

The first inner data message is a SOCKS-encoded destination address; the server
dials it and splices. DNS resolution happens server-side, keeping lookups off
the censored network.

## 7. What this prototype does NOT yet do

These are the honest gaps, each a research item rather than a solved problem:

- **TLS-in-TLS size/timing signature.** Framing inner traffic as app-data
  records hides the *content type* but not, on its own, the record-size and
  burst timing of an inner TLS session (the main modern passive attack). The
  padding-record mechanism exists; a shaping policy that actually imitates
  HTTP/2 browsing bursts is **not yet implemented**. This is the most important
  outstanding item.
- **Multiplexing.** Each tunnelled connection currently uses its own outer
  handshake. A stream mux over one connection is future work; until then, flow
  concurrency looks like many short TLS connections (which is not unlike a
  browser, but is not deliberately shaped).
- **Backend session tickets.** The handoff assumes the camouflage backend does
  not emit TLS 1.3 `NewSessionTicket` records mid-stream, which would race the
  switch. Pick a camouflage target that does not, or add ticket-draining.
- **Deployment checks.** There is no tool yet to verify the chosen SNI is
  plausible for the server's IP/ASN. An IP/SNI mismatch remains a cheap signal.
- **Formal analysis / real DPI evaluation.** The design has not been tested
  against nDPI, Zeek, or a GFW-style classifier. Do not deploy it where
  detection carries real risk.

## 8. Cryptography summary

- Authenticator: HMAC-SHA256, 16-byte tag, constant-time compare.
- Key schedule: HKDF-SHA256 bound to both handshake randoms.
- Record AEAD: ChaCha20-Poly1305, per-direction counter nonce.
- Outer fingerprint: uTLS Chrome (`HelloChrome_Auto`).
